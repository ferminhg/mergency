# Rename the classified activity event model for semantic clarity

ADR 0005 introduced `domain/models/event.py`'s `Event` (fields: `installation_id`, `repo`, `sha`, `event_type`, `owner`, `ts`) as the classified representation of a `build_failure` or `revert`, matching `ARQUITECTURE.md`'s `events` table one-to-one. Reviewing that code (`docs/plan/0009-event-classification.md`, PR #24), the class name `Event` reads as too generic at the code level: on its own, `from mergency.domain.models.event import Event` gives no hint that this is specifically a *classified GitHub repository activity record* feeding the budget pipeline — it could just as easily be mistaken for a raw webhook payload, a Python `asyncio.Event`, or some future unrelated domain event. This ADR decides between narrowing the name to fit the concept, versus widening the concept to fit a generic name.

## Status

📋 proposed

## Considered Options

- **Rename to a more semantic, narrower name (chosen).** `Event` → `ActivityEvent`, `EventType` → `ActivityEventType`, files `domain/models/event.py` → `domain/models/activity_event.py` and `domain/models/event_type.py` → `domain/models/activity_event_type.py`. This keeps the model's actual scope (a classified `build_failure`/`revert`/future-signal record tied to `installation_id`/`repo`/`sha`/`owner`/`ts`, per the `events` table) exactly as-is — only the identifier gets more specific, matching how `ARQUITECTURE.md`'s pipeline already calls this stage's output "activity events" flowing from `push`/`check_run`. Every dependent name follows the same rename for consistency: `EventRepository` → `ActivityEventRepository` (port), `InMemoryEventRepository` → `InMemoryActivityEventRepository` (adapter), and the Celery task/module `classify_activity_event.py` already uses the "activity event" phrasing, so it needs no change — it was arguably the tell that `Event` alone was under-naming the concept it classifies into.
- **Design a fully generic `Event` reusable for unrelated future event kinds (rejected).** The alternative reading of "make it generic" is to loosen `Event`'s shape (e.g. a generic payload/metadata bag, or a base class future unrelated events could extend) so it could represent things beyond classified repo activity — for instance a future budget-threshold notification, a config-change event, or anything else "event"-shaped the app might grow. Rejected: nothing on the roadmap needs this. ADR 0005 already made the model extensible in the one dimension that actually matters — `EventType` gaining `FLAKY_TEST` (ADR 0010) and a deploy-to-incident value (ADR 0011) later, still the same five-field shape tied to the same `events` table. A generic `Event` abstraction would either (a) grow optional/nullable fields to accommodate shapes that don't fit `installation_id`/`repo`/`sha`/`owner`/`ts`, blurring a currently well-defined single-purpose model, or (b) become an abstract base class with no current second subclass to justify it — speculative generality this codebase's YAGNI-leaning conventions (`CLAUDE.md`) explicitly avoid.
- **Leave `Event` as-is (rejected).** Doing nothing keeps the code exactly matching `ARQUITECTURE.md`'s own vocabulary ("the `events` table") and avoids a rename's churn across the repository/adapter/classifier/DI-wiring/test layers. Rejected because the naming concern is valid on its own terms — a bare `Event` import is genuinely ambiguous next to GitHub's own "webhook event" vocabulary already used throughout `webhooks.py`, `installation_command_parser.py`, and this same ADR's `check_run`/`push` events — and the rename is a small, mechanical, low-risk change while the feature is still unmerged (PR #24), which is the cheapest possible time to do it.

## Consequences

- `Event`/`EventType` and everything depending on them get renamed: `domain/models/event.py`, `domain/models/event_type.py`, `domain/ports/event_repository.py`, `adapters/memory/event_repository.py`, `domain/event_classifier.py`, `api/deps.py`'s `get_event_repository`/`get_event_classifier` factories (kept as-is if the accessor names read fine post-rename, or renamed to match — left to the implementation plan to decide), and every test file referencing these symbols. `classify_activity_event.py` (the Celery task) needs no rename.
- No change to the eventual Postgres schema (ADR 0007) — the `events` table name and columns stay exactly as `ARQUITECTURE.md` documents; only the Python domain identifier changes. Storage-layer vocabulary and code-layer vocabulary are allowed to diverge slightly here (table `events`, class `ActivityEvent`), same as `Installation`/`tenants` already do.
- ADR 0006, which references `` `Event` `` records by that literal backticked name, is not rewritten (ADRs are append-only per `CLAUDE.md`) — a reader encountering that reference after this rename lands should understand "`Event`" there refers to what is now `ActivityEvent`.
- This ADR does not implement the rename — it unblocks a follow-up `docs/plan/00XX-*.md` (TDD-first, one reviewable step per touched layer, same shape as `docs/plan/0009-event-classification.md`) to execute it, ideally before PR #24 merges to avoid a rename landing on top of already-released code.
